# 零 GC 运行时与编辑器工具链

有两条约束塑造了 AudioFlux 几乎每一个设计决策：运行时热路径不得分配，编辑器工具链必须足够好用，让设计师永远不必打开脚本去弄清音频在做什么。

## 为什么是零 GC（具体而言）

Unity 的音频回调运行在主线程上，而游戏过程中的垃圾回收会表现为帧时间尖峰，且很难归因到音频头上。目标是在稳态下，播放、停止、重新定位目标和设置音频参数**完全不产生托管分配**。

实现方式：

1. **固定容量音源池。** `AudioSourcePool` 只在构造时分配一次音源，之后以轮转方式复用。播放过程永不实例化组件。
2. **按值返回的结构体句柄。** 玩法代码收到的是 `AudioHandle` 值而不是类引用，因此请求播放不会创建日后需要 GC 追踪的堆对象。
3. **热路径上没有基于闭包的回调。** 播放路径中避免使用会捕获变量并产生分配的续体。
4. **内部可变，外部不可变。** `AudioHandle` 通过 getter 暴露声部状态，其可变字段保持 internal，因此句柄可以廉价复制，又不会把可变状态暴露给玩法代码。

## 为什么分析器会被编译剔除

埋点使用 `[Conditional("UNITY_EDITOR")]` 编写。调用点在源码中保留，因此代码保持可读、数据在编辑器中可用，但编译器会把这些调用从发行构建中完全移除。因此发布播放器不会为分析器付出任何代价——连一次空方法调用都不会有。

## 编辑器工具链

| 工具 | 用途 |
|---|---|
| `AudioProfilerWindow` | 日志视图加声部监视器：正在播什么、经由哪个事件、音量多少、以及为什么 |
| `AudioEmitterEditor` | 在 Inspector 中编写发声器及其空间设置，而不必手工编辑组件 |
| `SegmentScenePrefabScanner` | 扫描场景预制体中的音频相关对象，从而盘点一个场景的音频面（嵌套预制体实例不会被重复递归） |
| `AudioEmitterBatchAttacher` | 批量应用发声器配置，而不是一次一个对象 |
| `AudioEventLibraryImporter` | 把事件库导入到编写资源中 |
| `Tools/`（Bash CLI） | 用于从命令行对 Unity 项目执行 `setup` / `scan` / `validate` / `health` 的助手 |

设计意图与运行时一致：设计师应当无需询问工程师就能回答「正在播什么、为什么」，工程师应当无需打开编辑器就能校验一个项目的音频配置。

说明：批量扫描与导入工具对项目形态有感知。这里只做概述而不收录源码，因为它们的配置与某个特定生产项目绑定。
